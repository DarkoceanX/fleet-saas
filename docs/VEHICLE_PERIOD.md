# Техника и признанные затраты за период

Статус: реализованы расходный подэтап и фактические доходы/финансовый результат,
маршрут `/period`. Доходный контракт: [RECOGNIZED_INCOME](RECOGNIZED_INCOME.md).
Публичного размещения нет. Старый Python MVP и пользовательские SQLite не импортируются.

## Правила расчёта

- 26 групп из подтверждённого MVP 0.1.1; для собственной машины неприменима аренда
  самой машины, для арендованной — амортизация. Аренда навесного оборудования самостоятельна.
- Каждая ручная сумма — уже признанная часть расхода за указанную дату, с описанием
  основания. Страховка, общие расходы, проценты, амортизация распределяются вручную.
  Покупка актива и тело кредита не должны повторно попадать поверх амортизации.
  Специфические расходы отражаются описанными строками в подходящей группе или `other`.
- Даты включительны. Накопительные счётчики фиксируются на начало дня. Для сентября
  нужны именно 01.09 и 01.10; близкая дата не заменяет границу, интерполяции нет.
- `km`, фактические `work_hours`, справочные `engine_hours` независимы. Пустое значение
  = неизвестно, строка `0` = известный ноль. Каждый счётчик проверяется на монотонность
  по всей истории машины. Замена/сброс счётчика в этом подэтапе не поддерживаются.
- Один полный введённый total делится отдельно на км и рабочие часы. Моточасы
  двигателя не заменяют рабочие. При простое расходы остаются, ставка отсутствует.
- Деньги: строка, RUB, до 12 целых знаков и 2 дробных; PostgreSQL numeric(14,2).
  Счётчики: до 9 целых и 3 дробных, numeric(12,3). Суммы/деление Decimal precision 80.
  Ставка — 4 знака, half-up. Положительная ставка меньше точности отмечается флагом,
  UI показывает `< 0.0001`, не утверждает бесплатную эксплуатацию.
- Для каждой применимой группы: не проверено / проверено / затрат не было /
  неприменимо с причиной. Наличие строк само по себе не подтверждает полноту.
  Нельзя объявить положительную сумму нулём или неприменимой. Нулевая общая сумма
  даёт нулевую ставку только после актуального подтверждения всех групп.
- Подтверждение относится к точной паре дат и версии данных. Любая релевантная
  запись в организации консервативно сбрасывает все её подтверждения. Это может
  требовать лишней проверки другой машины, зато не сохраняет ложную полноту.

## Один фактический источник — один денежный эффект

`expenses` остаётся первичным реестром фактических расходов рейса. `vehicle_cost_entries`
хранит либо ручной расход машины, либо **ссылку**, а не копию суммы/даты рейса.
Уникальный `(tenant_id, trip_expense_id)` не позволяет признать источник дважды.
Планы, нормы, price и margin в этот реестр никогда не читаются.

1. В периоде показаны ещё не признанные фактические расходы рейсов назначенной машины.
   Бухгалтер явно выбирает одну из 26 групп и основание. Автосопоставления 7 рейсовых
   категорий с 26 группами нет. Их смысл может отличаться.
2. Машина периода выбирается явно. Ссылка запоминает исходное назначение рейса и
   категорию источника. После смены назначения расход не переезжает автоматически:
   прежняя машина получает предупреждение и блокировку подтверждения до перепроверки.
   Новая видит исходный ID, сумму и машину, за которой расход уже признан.
3. Дата `expenses.incurred_on` считается датой признания фактического расхода в этом
   управленческом реестре, а не датой платежа/создания записи/отправления рейса.
   Сумма и дата читаются из источника при каждом отчёте; void исключает расход.
   Текущий публичный способ исправления источника — void с причиной и новая запись.
   Прямое редактирование суммы/даты в fixture также проверено на правильное членство периода.
4. Если тот же первичный расход уже введён вручную, UI требует явно выбрать заменяемую
   ручную запись либо подтвердить, что такой записи нет. При замене сохраняется ID
   строки, её прежнее состояние — в аудите, локальная сумма/дата удаляются. Две записи
   не суммируются. Автоматического поиска дублей по чекам/тексту нет: без общего source ID
   разные ручные записи могут описывать один расход, это требует проверки пользователя.
5. Перепроверка изменённого назначения сохраняет ранее выбранную машину и обновляет
   снимок текущего источника. Перенос уже признанной ссылки между машинами отдельной
   операцией пока не реализован; требуются корректирующая отмена и новый источник с
   явным основанием. Молчаливого переноса истории нет.
6. Рейс без машины существующая схема запрещает NOT NULL + FK. При будущем nullable
   назначении нельзя подставлять машину: нужен явный нераспределённый источник.
   Расход, общий для нескольких машин, сейчас распределяется ручными долями с основанием;
   автоматическое расщепление одного рейсового source ID не реализовано.

## API и хранение

Все новые endpoints доступны только owner/accountant с SessionGuard. Tenant берётся
из membership; foreign IDs возвращают 404, запрещённые роли — 403. Composite FK
защищают машины, source expense и акторов. Для всех POST нужен UUID Idempotency-Key,
повтор с тем же содержимым возвращает предыдущий эффект, другое содержимое — 409.
Версия обязательна для изменения/удаления. Все записи и аудит транзакционны.

Префикс `/api/v1/vehicles/:vehicleId/period`:

| Метод/суффикс | Назначение |
|---|---|
| GET `?start_date=YYYY-MM-DD&end_date=YYYY-MM-DD` | Профиль, показания, источники, разбор и метрики |
| POST `/ownership` | owned/rented, version=0 для нового профиля |
| POST `/readings` | date, nullable строковые km/work_hours/engine_hours, note |
| POST `/readings/:id` / `/readings/:id/delete` | Изменение с version / удаление с version |
| POST `/costs` | date, category, amount строкой, currency=RUB, note |
| POST `/costs/:id` / `/costs/:id/delete` | Ручная коррекция / мягкое удаление, version |
| POST `/recognize` | expense_id/version, category, note, nullable replace_entry_id/version |
| POST `/review` | start/end, expected_revision, states[{category,status,reason}] |

Полный контракт validation — `packages/shared/src/period.ts`. Итоги и полнота всегда
охватывают весь выбранный период. С 01.11.2026 UI получает детализацию расходов и
доходов страницами; совместимый запрос без `page_size` сохраняет полный ответ.
Следующие страницы проверяют revision, при 409 требуется обновить отчёт.
[Контракт страниц](API.md#страницы-детализации-периода-01112026).
В форме признания можно догрузить записи для замены; выбранные ID/version сохраняются
при догрузке и обновлении отчёта. Изменённая/удалённая запись не превращается в новую:
сервер отклоняет устаревшую версию, пользователь повторно выбирает актуальную запись.
Смена машины/периода закрывает прежний редактор. Большие истории всё ещё требуют
нагрузочной проверки; серверные агрегаты читают полный набор.
Тип владения глобален для машины; смена при несовместимой истории затрат отклоняется.
Временная история собственности — будущая задача, старые периоды не переписываются.

Миграция `003_vehicle_period.sql` добавляет пять таблиц, индексы и триггеры revision.
Не заполняет автоматически владение, категории или связи старых расходов. Старые
тарифные снимки и расходы не переписываются. Отчёт, review и триггеры используют общий
advisory lock по tenant; обратной блокировки строк рейса в period service нет.
Это сериализует финансовые изменения внутри организации; нужен нагрузочный тест.
RLS не добавлен: как в существующем проекте, изоляция обеспечена API и composite FK.

Миграция применена **только в синтетической тестовой БД**, не в рабочей. Перед рабочим
применением: отдельный backup/restore drill, просмотр текущей схемы/checksums, план окна
блокировки на добавление триггеров, затем migration runner. При ошибке транзакция
откатывается. Старое приложение может продолжить работу с additive-схемой, но новые
period данные нельзя удалять down migration ради отката. Не применять setup/seed к
рабочей БД для активации этой функции.

## Доходы и результат — реализовано

Пользователь уточнил, что нужны оба уровня: рейс и техника за период, доход/расход.
Подэтап выполнен по следующему контракту; подробности API/коррекции —
[RECOGNIZED_INCOME](RECOGNIZED_INCOME.md):

- Новый первичный фактический доход: tenant, id, nullable trip_id, явный recognized_on,
  amount/currency, основание, version, void и audit. Плановая цена не создаёт такой доход.
- Доход рейса виден в рейсе и связан с машиной ровно один раз по source ID; вне рейса
  машина указывается явно. При смене назначения — та же политика фиксированной
  атрибуции, предупреждения и явной перепроверки, что у расходов.
- Периодизация дохода определяется recognized_on, а не departure_date или датой оплаты.
  Платёжный/налоговый учёт в эту модель не включается.
- Отдельные состояния полноты доходов: неизвестно, частично внесено, подтверждено,
  подтверждено отсутствие. Пустой реестр сам по себе не означает нулевой доход.
- `recognized_revenue - recognized_cost` — отдельный предварительный результат;
  при неизвестном доходе результат не определён. Итоговое подтверждение требует
  актуальной проверки обеих сторон. Себестоимость всегда `cost / km` и `cost / work_hours`.
- Добавлены миграция 004, API/roles/tenant/idem, UI рейса и периода, тесты
  суммы/даты/void/переназначения/повторов/неизвестного и нулевого дохода.
  Рабочее включение и ручная приёмка ещё не выполнены.

## Skills без расширения набора

Существуют шесть: `fleet-plan`, `fleet-costing`, `fleet-data`, `fleet-api`, `fleet-ui`,
`fleet-release`. Внешние skills не устанавливались; новые дублирующие инструкции не созданы.
28.10.2026 эти требования включены в существующие skills. Таблица задаёт направления
проверки при соответствующих изменениях, а не заявляет новые выполненные тесты:

| Skill | Закреплённая ответственность |
|---|---|
| fleet-plan | Разделять cost, revenue и profit; фиксация source/date/vehicle policy до API |
| fleet-costing | Ссылка на этот контракт, 26 групп, точные границы, 0≠unknown, golden fixtures |
| fleet-data | Уникальные источники, replace/void, revision и concurrency; реальный restore drill |
| fleet-api | Таблица каждого endpoint × role × foreign tenant, lost-response retry и stale version |
| fleet-ui | Жизненный цикл Add/Edit/Cancel/Delete/Add; stale fetch, смена машины, lost response |
| fleet-release | Явный test DB opt-in, реальные counts, upgrade/restore и ручная приёмка |

Отдельный новый skill сейчас не нужен. Будущую потребность в интеграциях/импорте и
нагрузочной безопасности разумно определить после появления соответствующего кода.
