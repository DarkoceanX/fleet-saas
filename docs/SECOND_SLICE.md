# Этап 2 — назначение, выполнение и план/факт

Исторический срез второго этапа: формулировки «пока не учитывается» и результаты
проверок ниже относятся к нему. Следующее расширение добавило
[периодические расходы](VEHICLE_PERIOD.md) и [фактические доходы](RECOGNIZED_INCOME.md).
Актуальное состояние исходников и рабочего включения: [CODEX_HANDOFF](CODEX_HANDOFF.md).

Цель: из карточки себестоимости сменить машину и назначить водителя, провести
рейс по статусам и сравнить сохранённый план с введёнными расходами.
База: локальная версия первого этапа, без .git. Соседние проекты не меняются.

План: аддитивная миграция → контракты и API → карточки водителей/рейсов и расходы →
тесты изоляции, конкурентности и обновления существующей БД → локальная приёмка.

## Решения и права

- Водитель: имя/обозначение и уникальный внутри организации табельный код.
  Документы, телефоны и прочие персональные сведения не собираются.
- Owner/dispatcher создают и изменяют водителей, назначения и статусы.
  Все роли читают операционные данные. Только owner/accountant видят и пишут финансы.
- Машина/водитель/маршрут изменяются только до выезда (draft/planned), с version.
  Смена машины не подставляет новые ставки: тарифы по-прежнему вводятся вручную.
- Статусы: draft → planned → in_progress → completed; draft/planned → cancelled.
  Для planned нужен активный водитель. Завершение и отмена необратимы в этом этапе.
  На отмене обязательна причина; все переходы записываются в историю.
- В отсутствие интервалов окончания один ресурс может иметь только один рейс
  planned/in_progress одновременно, независимо от даты. Это консервативная
  блокировка до завершения/отмены; альтернативу с календарём интервалов откладываем.
- Исторические планы неизменны. Новые планы сохраняют назначение, маршрут и его
  редакцию. До выезда сравниваем с последним планом текущей редакции; на выезде
  фиксируем его ID. Без подходящего плана рейс можно начать, сравнение показывает
  «нет плана». Старые снимки первого этапа не получают выдуманную историю назначений.
- Факт: отдельные положительные суммы RUB с точностью до копейки, дата, категория,
  обязательное основание. Никаких автоматических начислений из формулы плана.
  Расходы можно добавлять в любом статусе, включая поздние расходы завершённого
  или отменённого рейса; они не меняют его операционные данные.
- Исправление: аннулирование расхода с обязательной причиной и новой записью
  аудита, затем при необходимости новый расход. Исходные данные не удаляются.
  Идемпотентность защищает повтор добавления и аннулирования.
- Факт без записей — «не внесён», а не подтверждённая экономия. Разница = факт − план;
  категории без записей также остаются пустыми, а не нулевыми.
  процент относительно плана, null при нулевом плане. Факт — только введённая часть,
  без утверждения полноты закрытия. Фактическая выручка пока не учитывается.

## Приёмка

- Смена автомобиля в карточке, назначение водителя и статусы работают из UI.
- Чужие driver/trip/expense IDs не читаются и не изменяются; FK запрещают чужие связи.
- Конкурентное планирование не резервирует один ресурс дважды; устаревшая version — 409.
- Повтор расхода не дублирует сумму; аннулирование учитывается ровно один раз.
- Старые планы и данные первого этапа сохраняются после миграции.
- Эталон 23980.00 RUB не меняется. Факт 25000.00 даёт +1020.00 / +4.25%.
- Выполнены typecheck, lint, unit, integration, build, starter checks и браузерная приёмка.

Миграция 002 расширяет схему без удаления данных, nullable поля не требуют
восстановления неизвестных исторических назначений. Краткие блокировки ALTER TABLE
выполняются при остановленном локальном приложении. Перед обновлением — pg_dump.
Миграции транзакционны; при ошибке весь новый файл откатывается. Старую версию
приложения после новых статусов не запускать; восстановление — отдельная БД из дампа
и код первого этапа. RLS по-прежнему не включена.
