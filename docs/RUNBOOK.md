# Локальный Fleet SaaS

Локальная основа: вход, машины, водители, назначения, статусы рейсов, плановая
себестоимость, фактические расходы и сравнение план/факт. В исходниках также есть
периодические расходы/доходы; их рабочее включение отдельно описано ниже.
Приложение использует Next.js 16, NestJS 11, TypeScript 5.9 и PostgreSQL 17.
Проверенные версии зависимостей фиксирует package-lock.json. Нужен Node.js 24,
Python 3.11+ для сравнения с эталоном; PowerShell 7 для локальных Windows-скриптов.

## Первичная настройка Windows

Команды выполняются из корня starter:

```powershell
Set-Location 'D:\Logistic\fleet-saas-hybrid-codex-starter'
npm ci
```

Скачайте Windows x64 binaries PostgreSQL 17 с
[официальной страницы EDB](https://www.enterprisedb.com/download-postgresql-binaries)
и распакуйте каталог pgsql в work/pgsql. Это локальная копия, системная служба
не создаётся. Источник Windows-сборок указан также на
[postgresql.org](https://www.postgresql.org/download/windows/).

```powershell
./scripts/setup-local.ps1
npm run db:migrate
npm run db:seed
$env:NEXT_TELEMETRY_DISABLED='1'
npm run build
./scripts/start-local.ps1
```

Откройте http://localhost:3000. API слушает только 127.0.0.1:4000,
PostgreSQL — только 127.0.0.1:55432. Браузер обращается к API через Next.js.
Origin для изменения данных должен совпадать с APP_BASE_URL; используйте именно
localhost:3000, а не 127.0.0.1:3000. Данные сохраняются в work/pgdata.

setup-local.ps1 создаёт .env только при отсутствии: случайный пароль БД,
случайный SESSION_SECRET и пароль синтетических пользователей. .env и work/
игнорируются Git. Скрипт не перезаписывает существующие настройки.

## Тестовый вход

Общий пароль демонстрационных учётных записей: `FleetDemo2026!`.
Он предназначен только для этой локальной синтетической базы. Другой пароль
можно задать в DEMO_PASSWORD до первого seed. Повторный seed не меняет пароли.

| Роль | Север | Вектор |
|---|---|---|
| Владелец | owner@sever.demo | owner@vector.demo |
| Диспетчер | dispatcher@sever.demo | dispatcher@vector.demo |
| Бухгалтер | accountant@sever.demo | accountant@vector.demo |
| Наблюдатель | viewer@sever.demo | viewer@vector.demo |

Войдите владельцем → Автопарк → Добавить машину → Рейсы → Создать рейс →
Расчёт → Взять пример → Рассчитать и сохранить. После перезагрузки результат
останется доступен в истории. Пример: 23980.00 RUB, цена 29975.00 RUB.
Диспетчер не читает финансы, бухгалтер не меняет автопарк, наблюдатель не пишет.
Матрица первого этапа: [FIRST_SLICE.md](FIRST_SLICE.md). Расширение и правила
второго этапа: [SECOND_SLICE.md](SECOND_SLICE.md).

В карточке рейса можно сменить машину, назначить водителя и сохранить назначение.
Ставки остаются ручными: сохраните новый расчёт для текущего назначения. Затем
«Запланировать» → «Начать рейс» → «Завершить рейс». Переход подтверждается в форме.
До выезда доступна отмена с причиной. Машина/водитель заняты до завершения/отмены.

Вкладка «Факт и сравнение» позволяет добавить расходы по категориям, дате и основанию.
Ошибочная запись аннулируется с причиной, оставаясь в истории. План фиксируется
при выезде; поздний факт не меняет план. Без подходящего плана или без внесённого
факта вместо выдуманного отклонения показывается отсутствие данных.

## Повторный запуск и остановка

```powershell
Set-Location 'D:\Logistic\fleet-saas-hybrid-codex-starter'
./scripts/start-local.ps1
./scripts/stop-local.ps1
```

start-local запускает собранные API и интерфейс скрытыми процессами и записывает
их PID и время старта в work/app-processes.json. stop-local останавливает только
эти процессы с совпадающим временем старта и PostgreSQL с каталогом work/pgdata.
Данные не удаляются. Логи: work/api.log, work/api-error.log, work/web.log,
work/web-error.log, work/postgres.log.

Для разработки после остановки собранного приложения:

```powershell
./scripts/setup-local.ps1
npm run dev
```

Ctrl+C останавливает интерфейс и API. Базу останавливает stop-local.ps1.
Next.js обновляется автоматически; после правок API/shared перезапустите npm run dev.

## Проверки

```powershell
npm run typecheck
npm run lint
npm test
npm run test:integration
npm run build
python scripts/check_starter.py
python -m unittest discover -s tests -v
python scripts/calculate_trip.py examples/trip-cost.json
```

Интеграционные тесты требуют отдельную локальную БД `fleet_period_test` и явно
заданный `PERIOD_TEST_DATABASE_URL` на localhost/127.0.0.1. Они не читают `.env`
и не используют рабочий `DATABASE_URL` как запасной вариант. Пример только для
заранее подготовленного изолированного тестового кластера:

```powershell
$env:PERIOD_TEST_DATABASE_URL='postgresql://TEST_USER@127.0.0.1:TEST_PORT/fleet_period_test'
npm run test:integration
$env:CHROME_BIN='C:\Program Files\Google\Chrome\Application\chrome.exe'
npm run test:period:browser
```

Подставьте тестовый порт/пользователя. Не запускайте setup/seed для рабочей базы
ради тестов. Browser-тест создаёт собственный временный профиль и синтетический
transport, не подключается к API/БД. Интеграционные тесты создают отдельную схему
fleet_test_<случайный UUID>, выполняют настоящие
HTTP-запросы к NestJS на свободном порту и удаляют только эту схему в finally.
Демонстрационные записи не меняются. Пользователю БД нужно право CREATE SCHEMA.
RLS не включена; проверяются прикладные tenant-фильтры и составные FK.

## Миграции и восстановление

001_initial.sql — аддитивная первая схема; 002_operations.sql добавляет второй этап.
003_vehicle_period.sql добавляет расходный модуль периода. Его рабочее применение
ещё не выполнено; правила, блокировки и recovery-план: [VEHICLE_PERIOD](VEHICLE_PERIOD.md).
004_recognized_income.sql добавляет первичные фактические доходы и их проверки
полноты: [RECOGNIZED_INCOME](RECOGNIZED_INCOME.md). Также не применена к рабочей БД.
До обновления существующей БД выполните `node scripts/backup-local.mjs`.
Дамп сохраняется в work/backups. Сначала проверьте восстановление в отдельной БД,
затем согласуйте окно обновления и выполните db:migrate для проверенной целевой БД,
build и контролируемый перезапуск приложения. Не запускайте setup-local/seed для
обновления существующих пользовательских данных. Здесь эти действия не выполнены.
Существующие рейсы, машины и расчёты сохраняются. Старые расчёты не получают
выдуманные снимки назначения: эти поля остаются пустыми. Мигратор применяет файлы
по порядку в транзакции под advisory lock,
проверяет checksum уже применённых файлов. Повторный запуск безопасен.
При ошибке транзакция откатывается, версия не отмечается применённой. Исправьте
новую неприменённую миграцию и повторите. Применённые файлы не редактируйте.
Рабочая схема по передаче включает этапы 1 и 2; исходники содержат также 003/004.
Фактически применённые версии сверяйте с целевой БД; изменения делайте expand-first.

Для сохранения локальной БД перед будущими изменениями используйте pg_dump с
форматом custom и пароль через PGPASSWORD (не через историю команд). Для
восстановления создайте отдельную пустую БД и выполните pg_restore, затем проверки.
Автоматические резервные копии и production-восстановление пока не настроены.
Не удаляйте work/pgdata для обновления приложения.

## Проверка восстановления перед рабочими миграциями

Это процедура для отдельно разрешённой задачи с БД, не результат выполненной проверки.
Правка документации или наличие команды в RUNBOOK не разрешают рабочую миграцию.

1. Зафиксируйте источник: схему/версии и checksums миграций, совместимую сборку,
   ожидаемые контрольные показатели. Укажите конкретные хост, порт и имя источника
   и отдельной цели восстановления без паролей. Подготовьте изолированный экземпляр
   PostgreSQL и новую пустую БД; убедитесь, что цель не является рабочей БД.
2. Для разрешённого локального источника используйте существующий
   `node scripts/backup-local.mjs`: он рассчитан на локальную `fleet_saas` и
   `work/pgsql/bin/pg_dump.exe`. Для иной цели сначала подготовьте отдельную проверенную
   команду, не ослабляйте защиту скрипта. Зафиксируйте код завершения, время и SHA-256
   custom-дампа. Не выводите пароль/полный URL; дамп содержит исходные данные и не
   должен попадать в Git, скриншоты или внешние отчёты.
3. Проверьте наличие совместимого `pg_restore` и содержимое дампа, затем восстановите
   его в выбранную пустую БД. Параметры подключения и владения должны соответствовать
   изолированной среде; не применяйте очистку рабочей БД или восстановление поверх неё.
   Зафиксируйте полный результат процесса; список содержимого дампа не заменяет restore.
4. Сверьте восстановленные версии миграций, таблицы, ограничения/индексы/триггеры,
   количества источников и аудита, связи tenant и уникальность источников. Сравните
   суммы по tenant/машине/периоду, void, даты признания, сохранённые планы и состояния
   полноты с контрольными показателями того же снимка. Обеспечьте согласованность
   сравнения при изменяемом источнике; не сравнивайте разные моменты как один снимок.
5. На изолированной копии проверьте совместимую версию приложения и, если это входит
   в задачу, upgrade 003/004 и повтор мигратора. Проверьте один эффект источника,
   сохранность старой истории, роли и tenant-изоляцию. Для источника без 003/004
   недостающие сценарии проверяйте синтетическими данными в отдельной тестовой среде.
   Автоматические integration-тесты запускайте только на `fleet_period_test` с явным
   `PERIOD_TEST_DATABASE_URL`, не на восстановленной копии рабочих данных.
6. Сохраните обезличенный отчёт: снимок/хеш дампа, цель, команды без секретов,
   результаты сравнения, длительность восстановления, ошибки и непроверенные пункты.
   Не заявляйте выполнение RPO/RTO до согласования целей и измерения. При ошибке
   остановите рабочее применение; повторяйте drill в проверенной изолированной цели.
   Удаление дампа или восстановленной БД требует согласованной политики хранения.
7. Только после успешного drill и в пределах разрешённого обновления применяйте
   миграции/сборку/контролируемый перезапуск к проверенной рабочей цели. Восстановление
   данных и возврат версии кода планируйте вместе; destructive down не является recovery.

Автоматизированного restore-скрипта сейчас нет. Конкретные команды восстановления
составляются после проверки цели, инструментов и прав; этот документ их не выполняет.

## Границы доказательств

Для изменения только инструкций достаточно проверки структуры skills, frontmatter,
локальных ссылок и согласованности контрактов. `python scripts/check_starter.py`
не проверяет приложение; `--integrity` предназначен для исходной поставки и после
согласованных правок ожидаемо обнаруживает отличия. MANIFEST исходной поставки
не перезаписывайте для получения формального PASS.

В отчёте указывайте дату, источник (commit или хеши), среду, точные команды,
pass/fail/skip и причины пропусков. Разделяйте unit, HTTP+БД, Chrome DOM с mock
transport, реальный UI+API, visual/mobile, нагрузку и restore drill. Для mobile
фиксируйте браузер и размеры viewport, доступность действий/полей/ошибок и таблиц.
Исторические 30 unit / 63 integration / 18 DOM относятся к staging 24.10.2026,
не к новой проверке рабочей копии. Подготовленная процедура не означает её прохождения.

## Ограничения этапа

- Только локальная среда. Нет публичного размещения, OIDC, регистрации,
  приглашений, восстановления пароля и переключения организации.
- Серверная сессия 12 часов, HttpOnly/SameSite cookie; Secure применяется при HTTPS.
  Ограничение входа хранится в памяти одного API-процесса.
- Локальный пользователь PostgreSQL создан initdb и имеет повышенные права.
  Перед production нужны отдельная минимальная роль приложения и управление секретами.
- Бронирование консервативное: один planned/in_progress рейс на машину и водителя,
  независимо от даты. Интервалы времени и календарь загрузки ещё не реализованы.
- Завершённые и отменённые рейсы не переоткрываются. Расходы исправляются
  аннулированием с причиной и новой записью; исходная история сохраняется.
- Нет файлов чеков и налогового учёта. Фактические доходы и пользовательские проверки
  полноты доходов/расходов периода реализованы в модулях 003/004; рабочее включение
  требует отдельно согласованного применения миграций и обновления сборки.
- RUB без налогов, фиксированная формула v1. Справочника тарифов нет:
  manual-v1 означает снимок введённых ставок. Расчёты только добавляются.
- Списки постраничные; сводные цифры в интерфейсе показывают загруженные записи.
- Телеметрия Next.js выключена в скриптах запуска; платежи и внешние интеграции отсутствуют.

Требования версий сверены с метаданными npm и официальными справками
[Next.js](https://nextjs.org/docs/app/getting-started/installation) и
[NestJS](https://docs.nestjs.com/migration-guide). Node.js 24 удовлетворяет
минимальным требованиям установленных Next.js 16 и NestJS 11.
