## Источники и продуктовые решения

Расход рейса остаётся в `expenses`. Период хранит уникальную ссылку
`(tenant_id, trip_expense_id)`, читает живые сумму/дату `incurred_on` и void.
Дата трактуется как дата признания, не платежа/отправления. Категория выбирается
явно: 7 рейсовых групп нельзя автоматически угадать как 26 периодических.
Ручной дубль заменяется ссылкой с сохранением истории в аудите. Машина закрепляется
при признании; смена назначения рейса не переносит сумму молча, вызывает предупреждение
и перепроверку. Новая машина видит, где источник уже учтён. Плановые суммы исключены.

Реализованная модель доходов: единый первичный фактический доход с tenant,
source ID, nullable trip_id, явными recognized_on и машиной, amount/currency,
основанием, version/void/audit. В рейсе и периоде показывается один источник, а не
две копии. Для вне рейса машина выбирается явно. Переназначение требует той же
прозрачной политики, что расход. Пустой реестр = неизвестно, нулевой доход требует
подтверждения. `доход − расходы` — отдельный результат; неизвестный доход даёт
неопределённый результат. Себестоимость остаётся `расходы / выработка`.
Уникальный source_ref (номер основания, trim/upper) защищает от повторного ввода
того же источника как ручного и рейсового. При наличии записей без подтверждения
доход и результат помечены как частичные. Историческое revenue в cost_estimates
остаётся плановым; отдельного старого actual_revenue в схеме starter не было.

Риски: ручные записи без общего source ID могут дублировать один чек; автоматического
распознавания нет. История смены владения, распределение одного источника между
машинами, перенос признанной ссылки расхода отдельной командой пока не поддержаны.
Для дохода явный перенос машины/даты/связи с рейсом поддержан через update с причиной.
Review инвалидируется консервативно по всему tenant; нужен нагрузочный тест.
Полная детализация периода пока без пагинации. Restore drill, ручной UI+API smoke,
mobile/layout и production readiness не подтверждены.
