# Фактические доходы рейса и машины — реализовано 24.10.2026

Доходы реализованы отдельными первичными записями, не копиями между модулями.
`recognized_income` содержит tenant, id, vehicle_id, nullable trip_id, recognized_on,
amount/currency, source_ref, основание, version, void и аудит. Рейс фильтрует этот
реестр по trip_id; период — по закреплённой машине и дате признания. Один source ID
попадает в агрегат ровно один раз. Все записи RUB/decimal, до 12 целых и 2 дробных.

## План, факт, частичные суммы

В исходном starter не было отдельного фактического `actual_revenue` в БД. Значения
`cost_estimates.input_snapshot.revenue`, `result.revenue` и `actual_margin` принадлежат
снимку калькуляции; UI обозначает выручку и прибыль как плановые. Они **не импортируются**
в фактический доход и не датируются автоматически отправлением рейса. Исторические
снимки сохраняются без изменения. Если внешний старый файл когда-либо содержит поле
actual_revenue, его импорт требует отдельного явного признания/связи и не реализован.

Без неаннулированных доходов и текущего подтверждения отсутствия `actual_revenue=null`,
`financial_result=null`. При внесённых записях возвращается их сумма со статусом
`partial`: это введённая часть, а не автоматически полный доход. Даже строка дохода
с суммой 0 не подтверждает полноту. В периоде доступны отдельные проверки:
confirmed / zero / unreviewed, с основанием и expected_revision. Положительную
сумму нельзя подтвердить как отсутствие. Актуальный подтверждённый ноль даёт 0.00.

Результат периода = введённый/подтверждённый доход − введённые расходы. Он предварительный,
пока **обе** стороны не подтверждены на текущей версии. При подтверждённом отсутствии
доходов 50000 расходов означают результат −50000. Себестоимость остаётся gross:
50000 / 1000 km / 40 workh = 50/км и 1250/рабочий час при любом доходе.
Сумма 100000 дохода при таких расходах даёт отдельный результат 50000.

В рейсе отображаются все его доходы и результат относительно внесённых расходов
рейса. Без фактических расходов результат неопределён. Проверка полной доходности
рейса отдельной операцией не введена: его итог всегда помечен как предварительный;
полнота подтверждается для конкретной машины и периода. План/факт затрат и плановые
цена/маржа остаются в существующих экранах и API без изменения их смысла.

## Дата, машина и защита от дублей

- recognized_on — явная дата управленческого признания, не автоматически дата оплаты,
  рейса или ввода. Форма не подставляет её. Налоговый и платёжный учёт не реализованы.
- Машина выбирается явно; у связанного рейса сохраняется снимок его текущей машины.
  Последующее переназначение не переносит деньги молча, вызывает source_warning,
  invalidation и блокировку подтверждения. У новой машины показано, за какой другой
  машиной уже учтён доход.
- Изменение существующего дохода с version и причиной может явно сохранить/перенести
  машину, исправить дату/сумму, привязать вне-рейсовую запись к рейсу или отвязать её.
  ID остаётся тем же, старое состояние хранится в audit. Текущее назначение источника
  перепроверяется. Нельзя создавать вторую ручную копию суммы связанного рейса.
- source_ref — выбранный пользователем уникальный номер основания/строки документа.
  Канонизация trim + upper; UNIQUE(tenant_id,source_ref) работает между рейсовыми и
  вне-рейсовыми записями и сохраняется после void. При исправлении используйте update
  существующего ID; для нового корректирующего документа нужен новый собственный номер.
  Разные номера для одного экономического события не распознаются автоматически.
- Void требует версии и причины, исключает сумму из обоих представлений, сохраняет
  запись/историю. Повтор с тем же Idempotency-Key имеет один эффект.
- Любое изменение дохода/расхода/показаний/привязки инвалидирует проверки консервативно
  по tenant. Review доходов и затрат сами не увеличивают revision, поэтому обе проверки
  можно выполнить последовательно без взаимной отмены.

## API, UI и проверки

Владелец и бухгалтер; SessionGuard, tenant из membership, composite FK, UUID
Idempotency-Key для POST, version/reason для изменений. Другие роли — 403,
чужие ID — 404. Входные схемы: `packages/shared/src/income.ts`.

| Endpoint | Поведение |
|---|---|
| GET `/api/v1/trips/:id/income` | Те же источники, сумма и предварительный результат рейса |
| GET `/api/v1/vehicles/:id/period?start_date=...&end_date=...` | Дополнительный объект income: entries, summary, recognized_elsewhere |
| POST `/api/v1/income` | Явный первичный доход с vehicle_id, nullable trip_id, recognized_on, amount, currency, source_ref, note |
| POST `/api/v1/income/:id` | Те же поля + version, reason; одна коррекция существующего источника |
| POST `/api/v1/income/:id/void` | version, reason |
| POST `/api/v1/vehicles/:id/period/income-review` | start/end, expected_revision, status, reason |

UI доходов доступен в «Факт» рейса и в `/period`. При добавлении/исправлении расхода
рейса его доходный результат перечитывается. Списки машин/рейсов в форме имеют
«загрузить ещё». Форма сохраняет введённые значения/key при потере ответа; отмена
и новое добавление не сохраняют старый ID. С 01.11.2026 детализация доходов периода
в UI постраничная, включая аннулированную историю; доход и финансовый результат
по-прежнему вычисляются за весь период. [Контракт и конкуренция страниц](API.md#страницы-детализации-периода-01112026).
Рейсовый отчёт доходов не менялся. Пагинация непризнанных/чужих источников и нагрузка
больших историй остаются отдельной работой.

Миграция `004_recognized_income.sql` additive: две таблицы, индексы, trigger revision.
Ничего не переносит из планов. Проверены новая схема, upgrade со старым снимком,
tenant/roles/FK, source uniqueness, concurrency, date/edit/void/reassignment и
unknown/zero/partial. Результаты: [VERIFICATION_PERIOD](VERIFICATION_PERIOD.md).
Миграции 003/004 не применялись к рабочей БД. Перед рабочим включением нужны
backup/restore drill, проверка схемы и согласованное окно обновления.
